# 云端日志系统说明

> 用于排查线上用户问题，记录关键用户行为事件，可按邮箱查询完整操作时间线。

---

## 一、建表 SQL（首次部署需手动执行）

在 Supabase 控制台 → **SQL Editor** 中执行：

```sql
-- 云端日志表
create table if not exists user_logs (
  id          uuid default gen_random_uuid() primary key,
  user_id     text,
  user_email  text,
  device_id   text,
  event_type  text not null,
  payload     jsonb,
  created_at  timestamptz default now()
);

-- 查询索引
create index if not exists idx_user_logs_user_email on user_logs(user_email);
create index if not exists idx_user_logs_user_id    on user_logs(user_id);
create index if not exists idx_user_logs_created_at on user_logs(created_at desc);
create index if not exists idx_user_logs_event_type on user_logs(event_type);

-- RLS：只允许写入，不允许用户读取自己的日志
alter table user_logs enable row level security;

create policy "allow insert" on user_logs
  for insert to anon, authenticated
  with check (true);
```

## 二、日志事件类型说明

| event_type | 触发时机 | payload 关键字段 |
|---|---|---|
| `APP_OPEN` | 应用启动、获得 uid 后 | `isAnonymous`（是否匿名用户）、`activeTaskCount`（本地进行中任务数） |
| `APP_INIT_FAIL` | 初始化失败（网络不通、Supabase 错误） | `error`（错误信息） |
| `HYDRATE` | 云端拉取数据完成 | `result`（`"merged"` 本地+云端合并 / `"uploaded"` 云端无数据仅上传本地） |
| `START_TASK` | 用户点击「开始刷取」 | `planId`、`season` |
| `COMPLETE_TASK` | 用户点击「保存并查看」（出货完成） | `planId`、`spiritName`（出货精灵名） |
| `COMPLETE_AND_CONTINUE` | 用户点击「继续刷」（出货后不结束任务） | `planId`、`spiritName` |
| `ABANDON_TASK` | 用户点击「放弃任务」 | `planId` |
| `RECONCILE_ZOMBIES` | 检测到并清除了僵尸任务（planId 在墓碑里但仍残留于 activeTasks） | `count`（清除数量）、`planIds`（涉及方案）、`startTimes`（任务开始时间） |
| `SYNC_FAIL` | 数据上传连续重试 3 次仍失败 | `error`（错误信息）、`attempts`（重试次数） |
| `RECONNECT_OK` | 离线后重连 Supabase 成功 | `retryCount`（重试了几次） |
| `AUTH_LOGIN` | OTP 验证码登录成功（找回账号 / 换设备登录） | `prevUid`（切换前的旧 uid） |
| `AUTH_SWITCH` | 切换账号成功 | `prevUid` |

## 三、排查流程

### 3.1 准备

1. 打开 [Supabase Studio](https://supabase.com) → 进入项目 → **SQL Editor**
2. 向用户索取绑定的**邮箱**（未绑定邮箱的匿名用户可用 user_id，从 `user_data` 表查）

### 3.2 常用查询

**查某用户最近 50 条操作日志（按时间倒序）**

```sql
select created_at, event_type, payload, device_id
from user_logs
where user_email = '用户邮箱@qq.com'
order by created_at desc
limit 50;
```

---

**查某用户完整操作时间线（按时间正序，便于还原问题过程）**

```sql
select created_at, event_type, payload, device_id
from user_logs
where user_email = '用户邮箱@qq.com'
  and event_type in (
    'APP_OPEN', 'APP_INIT_FAIL',
    'HYDRATE',
    'START_TASK', 'COMPLETE_TASK', 'COMPLETE_AND_CONTINUE', 'ABANDON_TASK',
    'RECONCILE_ZOMBIES',
    'SYNC_FAIL', 'RECONNECT_OK',
    'AUTH_LOGIN', 'AUTH_SWITCH'
  )
order by created_at asc;
```

---

**排查「任务卡消失」问题：看是否触发了僵尸任务清理**

```sql
select created_at, user_email, payload
from user_logs
where user_email = '用户邮箱@qq.com'
  and event_type = 'RECONCILE_ZOMBIES'
order by created_at desc;
```

> 如果有记录，`payload.planIds` 就是被误删的任务方案 ID，`payload.startTimes` 是任务开始时间，可与 `payload` 里的墓碑时间对比确认是否为误判。

---

**排查「数据不同步」问题：看 HYDRATE 结果和 SYNC_FAIL**

```sql
select created_at, event_type, payload
from user_logs
where user_email = '用户邮箱@qq.com'
  and event_type in ('HYDRATE', 'SYNC_FAIL', 'APP_INIT_FAIL', 'RECONNECT_OK')
order by created_at desc
limit 30;
```

> - `HYDRATE.result = "uploaded"` 说明云端当时无数据，用的是本地上传
> - `SYNC_FAIL` 说明当时网络有问题，数据可能未及时上传
> - `APP_INIT_FAIL` 说明用户启动时就已经离线

---

**全局排查：查所有用户的僵尸任务清理事件（排查 Bug 影响范围）**

```sql
select created_at, user_email, payload
from user_logs
where event_type = 'RECONCILE_ZOMBIES'
order by created_at desc
limit 100;
```

---

**统计活跃用户数（最近 7 天）**

```sql
select count(distinct user_email) as active_users
from user_logs
where event_type = 'APP_OPEN'
  and created_at >= now() - interval '7 days'
  and user_email is not null;
```

---

**查某用户用了几台设备**

```sql
select distinct device_id, min(created_at) as first_seen
from user_logs
where user_email = '用户邮箱@qq.com'
group by device_id
order by first_seen;
```

---

## 四、注意事项

1. **匿名用户无邮箱**：`user_email` 为 null，需用 `user_id` 查询。`user_id` 从 `user_data` 表里找（让用户提供账号信息，或按设备 ID 反查）。

2. **日志为 fire-and-forget**：写入失败只打 console.warn，不影响业务逻辑，也不重试。极少数情况下日志可能缺失（网络瞬断时）。

3. **RLS 限制**：用户只能写入，不能读取日志，仅管理员可查。

4. **日志不会自动清理**：建议定期手动清理 90 天以前的数据，避免表过大：
   ```sql
   delete from user_logs where created_at < now() - interval '90 days';
   ```
